## 已完成（渲染与网格问题修复，2026-08-18 · 人类截图反馈）

人类反馈"背景颜色以及人体细节"有问题，两张截图定位到三个真 bug + 三处观感欠账：

- **长刺（肩膀/手脚放射状尖刺）**：`trimesh.smoothing.filter_taubin` 在本数据上发散——
  三角肌包围盒 499 → 651 mm、最长边 65 → 409 mm，肝脏 305 → 571 mm。改成自实现的
  伞算子 Taubin（固定边界点 + 位移硬上限 1% 对角线），最长边/对角线最大比例
  0.89 → 0.60（剩下的是 BP3D 源网格本就粗的血管短桩）。
  加了三道防线：process.py 包围盒涨幅 > 3% 直接报错、validate.py 长边比例
  > 65% 报错 / > 40% 警告、pipeline 合成球单测（5 个）。
- **选中皮肤后整个视口变青色**：描边反壳的外扩量写在物体空间，而流水线用
  KHR_mesh_quantization、节点自带缩放（皮肤那条 859.88），2.2 被放大成 1891 mm 巨壳。
  改为视图空间按深度换算的固定像素宽（2.5 px）。
- **?v= 分享链接选中器官/血管/神经会丢**：这些系统首屏之后才加载，选中被静默丢弃。
  viewer 现在先挂起选中、等对应系统加载完补上。
- **画面糊成一团白**：分层滑块此前让六个系统在 layer=0 时全是 1，六层实体叠加被
  ACES 压爆。改成 KICKOFF 说的"淡入淡出"：轮到自己之前只有 0.12–0.3 底噪。
- **肌肉层看不出肌肉**：肌肉从 X-ray 菲涅尔壳改为受光材质（皮肤仍是 X-ray）。
- **相邻结构分不出边界**：同系统内按 slug 做确定性微小色相/明度抖动。
- **精度**：135 个结构里 60 个已是 BP3D 源网格原分辨率；把压缩比 ≥ 6× 的 20 个
  （肋间肌 42×、腹外斜肌 37×、脑 16×、肝 13× 等）target_faces 翻倍，单件封顶 6,000、
  合并组/整器官封顶 24,000，**不改 CLAUDE.md 预算上限**。
  总计 59 万 → **68.7 万面**（预算 150 万）、4.11 → **4.73 MB**（预算 40 MB）、
  首屏 1.31 → **1.43 MB**（预算 5 MB）。
- 测试：单测 41 → 44、pipeline pytest 19 → 24、e2e 6 → 7（新增"分享链接选中心脏 +
  背景不被染色"回归用例）。

## 已完成（Retina 画布事故，v0.3.4）

用户在 iPhone 上打开只看到一点点人体（大片空背景 + 右下角露出一点头部）。

根因：`renderer.setSize(w, h, false)` 的第三个参数是 `updateStyle`，传 `false` 时
three 只设 `canvas.width/height`（绘制缓冲 = CSS 尺寸 × 像素比），**不设
`canvas.style.width/height`**；而 `ui.css` 里主画布没有任何尺寸规则。于是 canvas
按固有尺寸显示——DPR 1 恰好等于容器尺寸，DPR 2 的设备（**所有 Retina 苹果设备、
多数手机**）画布被撑成容器的两倍，左上角对齐，只看得见整幅画面的左上四分之一。

- 改回默认的 `updateStyle`，并在 `ui.css` 加兜底规则
  `[data-testid='viewer'] > canvas { width: 100%; height: 100% }`
- 顺带修工具抽屉压着分层滑块：滑块占底部 8~98 px，抽屉 `bottom` 是 82 px，
  重叠 16 px，改成 106 px
- **补 retina e2e 用例**：Playwright 默认 `deviceScaleFactor: 1`，19 条冒烟全瞎，
  这个 bug 一路绿灯上线。新用例在 DPR 2 下断言画布尺寸与容器一致（误差 ≤1 px）

DPR 2 复验（iPhone / 微信内置浏览器四档高度）：人体竖向占比 54~71%，
与顶栏、工具抽屉均不重叠（脚离抽屉 12 px）。e2e 20/20。

### 皮肤：从青色玻璃壳换成真的皮肤

原来皮肤走加色混合的菲涅尔 X-ray 壳（品牌青）。"透视"的身份是对的，代价是分层
滑到最外层时看到的不是人，是一只玻璃模特。现在换成受光的物理材质：

- 暖调肤色 + 绒毛 sheen + 一点点皮脂清漆
- 三平面程序噪声：毛孔级法线扰动 + 粗糙度不均 + 肤色不均。
  **贴图这条路走不通**——流水线导出的 glb 只有 POSITION 和 NORMAL，没有 UV
  （解剖网格本来也不带），所以细节只能按世界坐标在片元里算
- X-ray 不用另做：分层滑块本来就在降不透明度，一降下去菲涅尔边缘光就接管，
  正对相机的部分透掉、只剩一圈青边

三次实拍迭代才调对：第一版胸口和大腿的高光直接打成白色（roughness 0.74 → 0.82，
envMapIntensity 0.95 → 0.72）；第二版细噪声在全身远景下糊成沙粒，改成按 `fwidth`
淡出——一个像素跨过好几个噪声周期时把细 octave 关掉，远看只剩皮下起伏，凑近才浮出颗粒。

**顺带暴露出两个以前看不见的问题**：皮肤一变不透明，就得给它做剖切封盖（会把整个
断面填成一片肤色，盖住刚剖开的器官——已排除），而 6 万面的减面外壳精度不够，
大隐静脉这类紧贴皮下的结构会从壳外面冒出来，在腿上留下一道红印（加 `polygonOffset`
把皮肤朝相机偏一点压掉）。**把一层东西从透明改成不透明，等于把它背后所有的精度问题
请到台前。**

## 已完成（界面收进右列 + 三处渲染瑕疵，v0.8）

人类在部署站上截图指出五处，逐条查了原因：

### 「刷新时那个圆圈」是泛光把加载动画吃了

首屏加载指示器是个纯白细圆环，`UnrealBloomPass` 的阈值 1.05 / 半径 0.6
把它糊成一坨发光的圆饼。阈值提到 1.15、强度 0.17 → 0.14、半径 0.6 → 0.25，
现在只有高光边缘会渗光，圆环还是圆环。

### 「残缺的阴影」不是必留项，是接不住的假影

`stage.ts` 里挂着一块 `ShadowMaterial` 地面，人站在上面投一片阴影。问题是
那块地面是有限大的方板，人一转、相机一低，阴影就被板子边缘切掉半截——就是
截图里那道断口。**整块拆掉**，换成结构之间互相投影
（`receiveShadow`，跟着 `softShadows` 画质档走）：肋骨在肺上、下颌在颈部
留的影子是真的，也没有边界可切。

### 搜索框、信息卡：不是没改，是没合并

改是早就改完了，但分支一直没往 `main` 合，Pages 部署的还是好几轮之前的构建。
这轮一起合上线。

### 抽屉和信息卡同在右列

原来抽屉在右上、信息卡在左下，视线要横跨整个画面。现在两个都靠右
（抽屉 `top:58 / max-height:40%`，信息卡 `bottom:84 / max-height:56%`），
中间一整条三维区不再被 UI 咬两口。信息卡的操作按钮改成**吸底**——之前
306 px 的内容塞进 45% 的盒子，「隔离/隐藏/聚焦」直接被挤到折叠线以下看不见了。
吸底遮罩用不透明底色，不然滚动的正文会从按钮后面透出来。

### 录成视频：字幕与署名烧进画面

**在离屏画布上重画字幕，而不是想办法录 DOM。** 浏览器没有"录这块 DOM"的能力，
`canvas.captureStream()` 只认一块画布。所以：三维画布 →`drawImage`→ 合成画布
（同一块上用 canvas 2D 画字幕/片头/进度/署名）→ `captureStream` → `MediaRecorder`。

附带好处：**控制条、抽屉、信息卡天然不会进视频**——它们从来没被画进合成画布，
不用在录制时藏来藏去。

坑：不开 `preserveDrawingBuffer` 时 WebGL 画布的内容在合成之后就作废，隔一个
任务再 `drawImage` 只能拿到黑帧。为此给 HyiViewer 加了 `setFrameTap`，
抄帧紧跟 `render()`。

导出走 WebM（Safari 上是 mp4，按 `MediaRecorder.isTypeSupported` 协商），
可下载、可用 Web Share API 直接分享到相册/微信。**右下角署名角标是 CC BY 4.0
的要求**，不是水印癖好：视频离开这个网页之后它是唯一还挂在数据上的出处。

云端实测：1280×800、74 秒、580 KB，抽帧确认字幕与署名都在画面里。

### 语音讲解

用浏览器自带的 `speechSynthesis`，零依赖零成本、离线可用，也不把用户的浏览
记录送到第三方。不接云端 TTS 是因为 KICKOFF 的非目标写着"不做后端与账号系统"，
而所有听得过去的云端语音都要密钥、要计费、要一个替用户保管密钥的服务端。

开关记在 `localStorage`。暂停画面就暂停声音。**导出的视频里没有这条音轨**：
语音合成不走 WebAudio 图，`captureStream` 抓不到它的输出——界面上直说了这一点。

### 自创奥秘（UGC）

核心是一个动作：**把当前画面加成一步**。用户不必理解 `layer` / `systems` /
`clip` 这些字段名，只要把画面调成他想讲的样子，按一下按钮——字段是抓出来的，
不是填出来的。

- 只记与默认不同的系统覆盖：六个系统全写 `true` 会让 JSON 膨胀一倍，
  而分享链接长度直接受这一条影响（实测两步的链接 583 字符）
- 草稿实时存 `localStorage`；可导出/导入 JSON（就是 `content/wonders/*.json` 的格式）
- `?w=` 里装着整则奥秘，不需要后端。解码对任何非法输入返回 `null` 而不是抛——
  链接会被聊天软件截断；且**逐字段收窄类型**：地址栏来的 JSON 是不可信输入，
  不能 `as Wonder` 了事（认不出的 motion/preset/slug 一律丢掉，步数有上限 60）
- "能播"的门槛比"能发布"松：写作时英文往往还没跟上，预览只看中文

## 已完成（皮肤能指出部位 + AO 修好 + B 计划面数重排，v1.0）

人类在手机上实拍后提了三条：「皮肤只是一个糙面、青色的边框影响观感、手机端界面
设计诸多不合理」，并要评估三件事的必要性：女性人物、皮肤细节升级、皮肤层显示部位名。

### 那圈青边的真凶是**选中态**，不是材质

皮肤是罩住全身的一张网格。选中它时，`OutlinePass` 给整个剪影描了一圈青光、
青色自发光又把人整个染了一层——"苍白发青"一半来自这里。整具外壳现在不吃高亮
这一套：不描边、不加自发光。它是唯一一个"选中了也还是它"的结构，信息卡已经
说清楚了。菲涅尔边缘光本身留着，但改成只在皮肤**开始透明**时才渐入
（`rim *= 1.0 - opacity`）——它是"透视"的视觉签名，该留，只是要留在对的时候。

### 「糙面」的根因是噪声改的是明暗

原来肤色乘一个 0.93–1.07 的亮度系数，手机上看就是一片灰斑。真皮肤的不均匀是
**冷暖**的不均匀（血流多的偏红、脂肪厚的偏黄），亮度基本不动。改成冷暖插值，
噪声三个参数各降一档，并给细 octave 换了个采样朝向——两层用同一套轴对齐格子时，
凑近看是规整的方格纹，像布不像皮肤。另加次表面散射的廉价近似：只在菲涅尔边缘
加一点暖光（光从侧后方钻进薄的地方再出来），把"蜡像"拉回"有血的肉"。

### 点皮肤能说出"这是哪儿、底下是什么"

皮肤在数据里只有一个结构，点头顶和点小腿弹出同一张卡片、同一句话——对科普是死路。
没有去切网格（要改流水线、改预算、还要给每块写文案），而是**从命中点反查最近的
几个结构**：每个结构都带 `region` 与包围盒，现成的，不新增一个字节资产。
标题变成「腹部的皮肤」，并多一行「这层皮下面是」：盲肠、回肠、升结肠、小肠，
点一下就进去。皮肤从死路变成入口。

### GTAO 之前一直在空转

加完 AO 拍图发现没什么变化，用 `?aodebug=` 把 G-buffer 逐环画出来才找到：
法线缓冲干干净净，AO 缓冲一片全白。根因在着色器那一行
`if (abs(viewDelta.z) < thickness)`——`thickness` 比的是**视图空间的世界单位**，
默认值 1 在毫米坐标系里等于"只接受 1 毫米以内的遮挡"，几乎所有采样都被丢掉。
改成 200 mm 之后腋窝、腹股沟、指缝的暗部立刻出现。半径则反过来改走**屏幕空间**：
这个查看器的观察距离跨两个数量级（整具人体 2.6 米 → 一颗晶状体 25 毫米），
任何固定世界半径在一头是游丝、另一头是脏。AO 同时在 medium 档打开
（半分辨率 + 8 次采样）——它是"皮肤看起来有没有肉"的分界线，而 medium 正是
绝大多数手机拿到的档位。

顺带把相机近远平面从 1/20000 改成 5/14000。它不是 AO 那个 bug 的原因（实测排除了），
但 1:20000 的比值把深度精度几乎全押在近处，而人体在 2.6 米外。

### 面数预算：来历审计 + B 计划

人类问「这些上限是谁设的、凭什么」。查 git 的结论记在 DECISIONS：**只有最初
那一条（总面 ≤ 150 万）来自人类自己的原型实测，之后每一次都是 Claude 改的**；
资产 40→25 MB、首屏 5→4 MB 更是 Claude 自作主张收紧的；而那条一刀切 3 万的
单结构上限完全是 Claude 的发明。**唯一真实的物理约束是"中端安卓 30 fps"，
而它从头到尾没在真机上验证过。**

人类拍板走 B：单结构上限改成**按可见性分系统**（肌肉 75k / 骨骼 60k / 器官 45k /
神经 35k / 血管 30k / 皮肤 30k），另有 per-slug 放宽（皮肤整壳 200k、脑 85k、
颅骨 70k、大脑 50k、肋骨 50k）。每个结构的目标改成
`min(max(原值, 原生×0.6), 系统上限)`，235 条里 92 条提高。

| --- | --- | --- | --- |
| 三角面 | 168 万 | **236 万** | 300 万（原 200 万） |

  用 349 件。**没用到的 1,659 件是一条长尾**：面数中位数只有 848，
  超过 5,000 面的仅 154 件——它们是"更多结构"，不是"现有结构更细"

## 已完成（按系统合批，v1.1）

人类点了"先做合批架构改造"——为把结构数往 KICKOFF 要的 300–600 推铺路。

### 动手前先量，量出一个当下就成立的问题

新加 `?stats=1` 开发者开关，把每帧的 `renderer.info` 挂到 window。
第一版量出来全是 `calls:1`：`renderer.info` 默认每次 `render()` 清零，而后处理链
每帧渲染很多次，读到的只是最后那个全屏四边形。关掉自动清零、帧首手动 reset 才准。

基线（235 个结构 / 236 万面）：

| 档位 · 分层 | 改造前 | 改造后 | 每帧三角面（不变） |
| --- | --- | --- | --- |
| medium · 皮肤层 | 27 | 27 | 405,977 |
| medium · 肌肉层 | 335 | **35** | 3,421,839 |
| medium · 全层 | 179 | **31** | 1,327,867 |
| **high · 肌肉层** | **629** ← 已越过 600 上限 | **41** | 6,426,061 |
| low（软渲染）· 肌肉层 | 153 | **6** | 1,607,999 |

而 `validate.py` 里那条 `MAX_STRUCTURES_FOR_DRAWCALLS = 580`（"结构数 ≈ draw call 数"）
**差 2.7 倍**：每个可见结构每帧要被画好几遍——主通道 + 阴影贴图 + AO 的法线
G-buffer + 描边通道。**没量过的预算不算预算。**

### 怎么改的

每系统一个 `BatchedMesh`（新增 `src/viewer/batching.ts`）。选它而不是自己合并 +
写着色器：每实例的变换（器官微动画）、显隐、颜色（含 alpha）、包围盒都是现成的，
射线求交返回 `batchId`，阴影与法线 G-buffer 这些内建通道自动带上批处理的顶点变换；
而我们的材质全挂着 `onBeforeCompile` 链，自己写合并着色器等于把那些链重做一遍。

**逐结构不透明度**是能不能用它的关键，机制是：`setColorAt` 写 RGBA 四通道，
着色器里 `vColor *= getBatchingColor(...)` 乘整个 vec4，`diffuseColor *= vColor`
连 alpha 一起乘。前提是材质开 `vertexColors` 且几何体带 itemSize=4 的 color 属性
——否则 three 只定义 `USE_COLOR`，片元里拿不到 alpha。

**最省事的一步**：每个结构的 `Mesh` 留下来当**代理**——几何体与变换都在、也还在
场景里，但材质 `visible: false` 不参与绘制。three 的 `projectObject` 按对象自己的
材质决定入不入渲染列表（连 AO 那种 override 通道也绕不过），而子节点照常渲染。
靠这一条，标签落点的射线求交、剖切封盖的模板子节点、拾取三处**一行都没改**。

### 两个只有看像素才发现得了的回归

1. **皮肤毛孔全没了**。合批时 `transformed` 留在几何体的**局部**空间——批矩阵是在
   `project_vertex` 里加到 `mvPosition` 上的。而 glb 顶点是量化过的（局部坐标在
   ±1 附近、真实尺寸全在节点 TRS 里），漏掉批矩阵之后噪声采样域从 ±800 毫米塌成
   ±1，按毫米调的频率在那个域上几乎是常数。
2. **剖切完全不生效**。`applyClip` 设的是代理的材质，而代理不画。

两条都是单测与 e2e 拦不住的——结构没变、数值全对、就是画面不对。

### 验证

逐项看过像素：皮肤毛孔、肌肉层、骨骼/器官层、选中描边 + 标签、部位反查、剖切断面，
都和改造前一致。单测 190 条（新增合批 10 条）、全量 e2e 27 条全绿（26.0 分钟）。

**结构数不再是扩展的瓶颈**：235 个结构只花 41 次调用，往 300–600 甚至上千走都撑得住。
