## 已完成（渲染与网格问题修复，2026-08-18 · 人类截图反馈）

人类反馈"背景颜色以及人体细节"有问题，两张截图定位到三个真 bug + 三处观感欠账：

- **长刺（肩膀/手脚放射状尖刺）**：`trimesh.smoothing.filter_taubin` 在本数据上发散——
  三角肌包围盒 499 → 651 mm、最长边 65 → 409 mm，肝脏 305 → 571 mm。改成自实现的
  伞算子 Taubin（固定边界点 + 位移硬上限 1% 对角线），最长边/对角线最大比例
  0.89 → 0.60（剩下的是 BP3D 源网格本就粗的血管短桩）。
  加了三道防线：process.py 包围盒涨幅 > 3% 直接报错、validate.py 长边比例
  > 65% 报错 / > 40% 警告、pipeline 合成球单测（5 个）。
- **选中皮肤后整个视口变青色**：描边反壳的外扩量写在物体空间，而流水线用
  KHR_mesh_quantization、节点自带缩放（皮肤那条 859.88），2.2 被放大成 1891 mm 巨壳。
  改为视图空间按深度换算的固定像素宽（2.5 px）。
- **?v= 分享链接选中器官/血管/神经会丢**：这些系统首屏之后才加载，选中被静默丢弃。
  viewer 现在先挂起选中、等对应系统加载完补上。
- **画面糊成一团白**：分层滑块此前让六个系统在 layer=0 时全是 1，六层实体叠加被
  ACES 压爆。改成 KICKOFF 说的"淡入淡出"：轮到自己之前只有 0.12–0.3 底噪。
- **肌肉层看不出肌肉**：肌肉从 X-ray 菲涅尔壳改为受光材质（皮肤仍是 X-ray）。
- **相邻结构分不出边界**：同系统内按 slug 做确定性微小色相/明度抖动。
- **精度**：135 个结构里 60 个已是 BP3D 源网格原分辨率；把压缩比 ≥ 6× 的 20 个
  （肋间肌 42×、腹外斜肌 37×、脑 16×、肝 13× 等）target_faces 翻倍，单件封顶 6,000、
  合并组/整器官封顶 24,000，**不改 CLAUDE.md 预算上限**。
  总计 59 万 → **68.7 万面**（预算 150 万）、4.11 → **4.73 MB**（预算 40 MB）、
  首屏 1.31 → **1.43 MB**（预算 5 MB）。
- 测试：单测 41 → 44、pipeline pytest 19 → 24、e2e 6 → 7（新增"分享链接选中心脏 +
  背景不被染色"回归用例）。

## 已完成（Retina 画布事故，v0.3.4）

用户在 iPhone 上打开只看到一点点人体（大片空背景 + 右下角露出一点头部）。

根因：`renderer.setSize(w, h, false)` 的第三个参数是 `updateStyle`，传 `false` 时
three 只设 `canvas.width/height`（绘制缓冲 = CSS 尺寸 × 像素比），**不设
`canvas.style.width/height`**；而 `ui.css` 里主画布没有任何尺寸规则。于是 canvas
按固有尺寸显示——DPR 1 恰好等于容器尺寸，DPR 2 的设备（**所有 Retina 苹果设备、
多数手机**）画布被撑成容器的两倍，左上角对齐，只看得见整幅画面的左上四分之一。

- 改回默认的 `updateStyle`，并在 `ui.css` 加兜底规则
  `[data-testid='viewer'] > canvas { width: 100%; height: 100% }`
- 顺带修工具抽屉压着分层滑块：滑块占底部 8~98 px，抽屉 `bottom` 是 82 px，
  重叠 16 px，改成 106 px
- **补 retina e2e 用例**：Playwright 默认 `deviceScaleFactor: 1`，19 条冒烟全瞎，
  这个 bug 一路绿灯上线。新用例在 DPR 2 下断言画布尺寸与容器一致（误差 ≤1 px）

DPR 2 复验（iPhone / 微信内置浏览器四档高度）：人体竖向占比 54~71%，
与顶栏、工具抽屉均不重叠（脚离抽屉 12 px）。e2e 20/20。

### 皮肤：从青色玻璃壳换成真的皮肤

原来皮肤走加色混合的菲涅尔 X-ray 壳（品牌青）。"透视"的身份是对的，代价是分层
滑到最外层时看到的不是人，是一只玻璃模特。现在换成受光的物理材质：

  **贴图这条路走不通**——流水线导出的 glb 只有 POSITION 和 NORMAL，没有 UV
  （解剖网格本来也不带），所以细节只能按世界坐标在片元里算
- X-ray 不用另做：分层滑块本来就在降不透明度，一降下去菲涅尔边缘光就接管，
  正对相机的部分透掉、只剩一圈青边

三次实拍迭代才调对：第一版胸口和大腿的高光直接打成白色（roughness 0.74 → 0.82，
envMapIntensity 0.95 → 0.72）；第二版细噪声在全身远景下糊成沙粒，改成按 `fwidth`
淡出——一个像素跨过好几个噪声周期时把细 octave 关掉，远看只剩皮下起伏，凑近才浮出颗粒。

**顺带暴露出两个以前看不见的问题**：皮肤一变不透明，就得给它做剖切封盖（会把整个
断面填成一片肤色，盖住刚剖开的器官——已排除），而 6 万面的减面外壳精度不够，

请到台前。**

人类在部署站上截图指出五处，逐条查了原因：

### 「刷新时那个圆圈」是泛光把加载动画吃了

首屏加载指示器是个纯白细圆环，`UnrealBloomPass` 的阈值 1.05 / 半径 0.6
把它糊成一坨发光的圆饼。阈值提到 1.15、强度 0.17 → 0.14、半径 0.6 → 0.25，
现在只有高光边缘会渗光，圆环还是圆环。

### 「残缺的阴影」不是必留项，是接不住的假影

`stage.ts` 里挂着一块 `ShadowMaterial` 地面，人站在上面投一片阴影。问题是
那块地面是有限大的方板，人一转、相机一低，阴影就被板子边缘切掉半截——就是
截图里那道断口。**整块拆掉**，换成结构之间互相投影
（`receiveShadow`，跟着 `softShadows` 画质档走）：肋骨在肺上、下颌在颈部
留的影子是真的，也没有边界可切。

这轮一起合上线。

### 录成视频：字幕与署名烧进画面

**在离屏画布上重画字幕，而不是想办法录 DOM。** 浏览器没有"录这块 DOM"的能力，
`canvas.captureStream()` 只认一块画布。所以：三维画布 →`drawImage`→ 合成画布
（同一块上用 canvas 2D 画字幕/片头/进度/署名）→ `captureStream` → `MediaRecorder`。

附带好处：**控制条、抽屉、信息卡天然不会进视频**——它们从来没被画进合成画布，
不用在录制时藏来藏去。

坑：不开 `preserveDrawingBuffer` 时 WebGL 画布的内容在合成之后就作废，隔一个
任务再 `drawImage` 只能拿到黑帧。为此给 HyiViewer 加了 `setFrameTap`，
抄帧紧跟 `render()`。

导出走 WebM（Safari 上是 mp4，按 `MediaRecorder.isTypeSupported` 协商），
可下载、可用 Web Share API 直接分享到相册/微信。**右下角署名角标是 CC BY 4.0
的要求**，不是水印癖好：视频离开这个网页之后它是唯一还挂在数据上的出处。

云端实测：1280×800、74 秒、580 KB，抽帧确认字幕与署名都在画面里。

### 语音讲解

用浏览器自带的 `speechSynthesis`，零依赖零成本、离线可用，也不把用户的浏览
记录送到第三方。不接云端 TTS 是因为 KICKOFF 的非目标写着"不做后端与账号系统"，
而所有听得过去的云端语音都要密钥、要计费、要一个替用户保管密钥的服务端。

开关记在 `localStorage`。暂停画面就暂停声音。**导出的视频里没有这条音轨**：
语音合成不走 WebAudio 图，`captureStream` 抓不到它的输出——界面上直说了这一点。

### 自创奥秘（UGC）

核心是一个动作：**把当前画面加成一步**。用户不必理解 `layer` / `systems` /
`clip` 这些字段名，只要把画面调成他想讲的样子，按一下按钮——字段是抓出来的，
不是填出来的。

- 只记与默认不同的系统覆盖：六个系统全写 `true` 会让 JSON 膨胀一倍，
  而分享链接长度直接受这一条影响（实测两步的链接 583 字符）
- 草稿实时存 `localStorage`；可导出/导入 JSON（就是 `content/wonders/*.json` 的格式）
- `?w=` 里装着整则奥秘，不需要后端。解码对任何非法输入返回 `null` 而不是抛——
  链接会被聊天软件截断；且**逐字段收窄类型**：地址栏来的 JSON 是不可信输入，

## 已完成（皮肤能指出部位 + AO 修好 + B 计划面数重排，v1.0）

人类在手机上实拍后提了三条：「皮肤只是一个糙面、青色的边框影响观感、手机端界面
设计诸多不合理」，并要评估三件事的必要性：女性人物、皮肤细节升级、皮肤层显示部位名。

### 那圈青边的真凶是**选中态**，不是材质

皮肤是罩住全身的一张网格。选中它时，`OutlinePass` 给整个剪影描了一圈青光、
青色自发光又把人整个染了一层——"苍白发青"一半来自这里。整具外壳现在不吃高亮
这一套：不描边、不加自发光。它是唯一一个"选中了也还是它"的结构，信息卡已经
说清楚了。菲涅尔边缘光本身留着，但改成只在皮肤**开始透明**时才渐入
（`rim *= 1.0 - opacity`）——它是"透视"的视觉签名，该留，只是要留在对的时候。

### 「糙面」的根因是噪声改的是明暗

原来肤色乘一个 0.93–1.07 的亮度系数，手机上看就是一片灰斑。真皮肤的不均匀是
**冷暖**的不均匀（血流多的偏红、脂肪厚的偏黄），亮度基本不动。改成冷暖插值，
噪声三个参数各降一档，并给细 octave 换了个采样朝向——两层用同一套轴对齐格子时，
凑近看是规整的方格纹，像布不像皮肤。另加次表面散射的廉价近似：只在菲涅尔边缘
加一点暖光（光从侧后方钻进薄的地方再出来），把"蜡像"拉回"有血的肉"。

### 点皮肤能说出"这是哪儿、底下是什么"

皮肤在数据里只有一个结构，点头顶和点小腿弹出同一张卡片、同一句话——对科普是死路。
没有去切网格（要改流水线、改预算、还要给每块写文案），而是**从命中点反查最近的
几个结构**：每个结构都带 `region` 与包围盒，现成的，不新增一个字节资产。
标题变成「腹部的皮肤」，并多一行「这层皮下面是」：盲肠、回肠、升结肠、小肠，
点一下就进去。皮肤从死路变成入口。

### GTAO 之前一直在空转

加完 AO 拍图发现没什么变化，用 `?aodebug=` 把 G-buffer 逐环画出来才找到：
法线缓冲干干净净，AO 缓冲一片全白。根因在着色器那一行
`if (abs(viewDelta.z) < thickness)`——`thickness` 比的是**视图空间的世界单位**，
默认值 1 在毫米坐标系里等于"只接受 1 毫米以内的遮挡"，几乎所有采样都被丢掉。
改成 200 mm 之后腋窝、腹股沟、指缝的暗部立刻出现。半径则反过来改走**屏幕空间**：
这个查看器的观察距离跨两个数量级（整具人体 2.6 米 → 一颗晶状体 25 毫米），
任何固定世界半径在一头是游丝、另一头是脏。AO 同时在 medium 档打开
（半分辨率 + 8 次采样）——它是"皮肤看起来有没有肉"的分界线，而 medium 正是
绝大多数手机拿到的档位。

顺带把相机近远平面从 1/20000 改成 5/14000。它不是 AO 那个 bug 的原因（实测排除了），
但 1:20000 的比值把深度精度几乎全押在近处，而人体在 2.6 米外。

资产 40→25 MB、首屏 5→4 MB 更是 Claude 自作主张收紧的；而那条一刀切 3 万的

而它从头到尾没在真机上验证过。**

### 怎么改的

每系统一个 `BatchedMesh`（新增 `src/viewer/batching.ts`）。选它而不是自己合并 +
写着色器：每实例的变换（器官微动画）、显隐、颜色（含 alpha）、包围盒都是现成的，
射线求交返回 `batchId`，阴影与法线 G-buffer 这些内建通道自动带上批处理的顶点变换；
而我们的材质全挂着 `onBeforeCompile` 链，自己写合并着色器等于把那些链重做一遍。

**逐结构不透明度**是能不能用它的关键，机制是：`setColorAt` 写 RGBA 四通道，
着色器里 `vColor *= getBatchingColor(...)` 乘整个 vec4，`diffuseColor *= vColor`
连 alpha 一起乘。前提是材质开 `vertexColors` 且几何体带 itemSize=4 的 color 属性
——否则 three 只定义 `USE_COLOR`，片元里拿不到 alpha。

**最省事的一步**：每个结构的 `Mesh` 留下来当**代理**——几何体与变换都在、也还在
场景里，但材质 `visible: false` 不参与绘制。three 的 `projectObject` 按对象自己的
材质决定入不入渲染列表（连 AO 那种 override 通道也绕不过），而子节点照常渲染。
靠这一条，标签落点的射线求交、剖切封盖的模板子节点、拾取三处**一行都没改**。

### 两个只有看像素才发现得了的回归

1. **皮肤毛孔全没了**。合批时 `transformed` 留在几何体的**局部**空间——批矩阵是在
   `project_vertex` 里加到 `mvPosition` 上的。而 glb 顶点是量化过的（局部坐标在
   ±1 附近、真实尺寸全在节点 TRS 里），漏掉批矩阵之后噪声采样域从 ±800 毫米塌成
   ±1，按毫米调的频率在那个域上几乎是常数。
2. **剖切完全不生效**。`applyClip` 设的是代理的材质，而代理不画。

两条都是单测与 e2e 拦不住的——结构没变、数值全对、就是画面不对。

- **PWA 构建被全量挂掉**：muscles.glb 9.45 MB 越过 workbox 的 8 MB 单文件上限。

- **`validate.py` 的父结构链会 KeyError**：父存在、祖父缺失就崩。对应单测断言的

- **新增 `data-hyi-loaded` 属性**：首屏只剩皮肤之后，"ready"与"画全了"之间隔着

- `BACKGROUND_ORDER` 排序：`indexOf` 找不到返回 −1，会把表外的系统排到骨骼前面。

### e2e 暴露的两件事（都不只是测试问题）

首屏只剩皮肤之后，"ready"与"看得见"之间隔了五个系统，两条选心脏的 e2e 因此变红：

1. **分享链接点名的结构要等十几秒才高亮**。`?v=…selected=heart` 里器官排后台
   第三位，要等骨骼(4.9)+肌肉(9.5)共 14 MB 下完才轮到。用户看到的是"信息卡
   写着心脏，画面里却什么都没高亮、标签也不来"。修法：App 在 `load()` 之前
   先解一次 `?v=`，把点名结构所在的系统插到后台队列最前
   （`HyiViewer.LoadOptions.prioritizeStructure`）。
2. **首屏口径其实写在三处**，不是两处：`validate.py`、查看器、
   `tests/unit/manifest.test.ts`。上一条一致性检查只覆盖了前两处，单测那份
   继续按"皮肤+骨骼"算、多算 4.9 MB——**它确实红了，但红的理由是错的**。
   现在抽出 `src/viewer/loadOrder.ts` 当唯一事实来源：查看器与单测直接 import，
   `validate.py` 读它核对（负向验证过：故意改回 skeleton 会报错）。
   排序逻辑同时抽成纯函数 `backgroundOrder()`，补了 8 条单测——它有两个容易
   写错的边界：`indexOf` 找不到返回 −1（会把陌生系统排到骨骼前面），
   以及点名的结构可能压根不在后台队列里（皮肤在首屏）。

修完之后 e2e 27 条全绿（22.2 分钟），而且**比修之前快得多**——因为点名的结构
不再排队等 19 MB：

| 用例 | 修复前 | 修复后 |
| --- | --- | --- |
| 分享链接选器官 | 失败两次（37.4s / 36.6s） | ✓ 9.2s |
| 信息卡 + 三维标签 | 失败 38.9s，重试 1.1m | ✓ 10.8s |
| 脊髓四段 | 失败 37.3s，重试才过 | ✓ 23.9s |
| 沿结构半剖 | 2.5m | 44.4s |
| 打开心脏 | 2.1m | 1.0m |

**e2e 整体仍然比 B 计划慢，这是真实代价**：软件渲染下 478 万面约 1.2 秒一帧，
Playwright 每个动作要等好几帧。奥秘那条（从菜单开播，链接里没点名结构、
享受不到上面那个优化）首跑 6.1 分钟、重试 4.0 分钟，卡在原来 360 秒预算的两边，
于是每轮都判一次"首跑失败、重试通过"——预算已抬到 600 秒。

那个视距下三角形早就小于一个像素——**面数不再是瓶颈**，v1.2 把额度花在了一个
本来就够用的轴上。

真正的瓶颈查 glb 才看清：

    muscles.glb 顶点属性：{'POSITION': 45, 'NORMAL': 45}
    材质数：1   贴图数：0   纹理采样器：0

**没有 UV，没有任何贴图，一个系统一个材质一个颜色。** 截图里那些肌纤维沟纹是
BP3D 原始扫描刻在网格上的，不是渲染出来的。除皮肤有一层程序化毛孔外，其余结构
全是纯色 + 一圈边缘光——整片腹肌同一个三文鱼粉，肌腱不反光、筋膜没明暗、骨面没质地。

### 做法：加着色，不加数据

三平面世界坐标噪声（皮肤那套的推广），按系统给不同的表面：

| 系统 | 主频 | 顺纹拉伸 | 要的是什么 |
| --- | --- | --- | --- |
| muscles | 1/3.2 mm | 9× | 顺纹的沟 + 腱膜偏白、肌腹偏深 |
| skeleton | 1/1.6 mm | 1×（各向同性） | 骨面孔隙 |
| organs | 1/9.0 mm | 1.6× | 大尺度湿润色斑 |
| vessels | 1/5.0 mm | 2.5× | 只让高光碎，不要花纹（管子起纹像波纹管） |
| nerves | 1/2.2 mm | 7× | 细密顺纹 |

**零字节、不碰流水线、不动体积预算**，代价只在逐片元开销上。颜色调制刻意
只动冷暖与饱和、不动亮度——皮肤那轮的教训：直接乘亮度出来的不是质感是脏点。

### 代价按画质档分级（QUALITY_CAPS.surfaceDetail）

    low     0  完全不注入。软件渲染兜底档，**e2e 正好跑这一档，所以测试不会变慢**
    medium  1  1 次噪声 + 单轴差分法线
    high    2  叠第二个八度 + 三轴梯度

档位用 **uniform** 而不是编译期分支：高画质开关随时能拨，而材质是系统加载时
建好的——编译期分支意味着用户拨了开关什么都不变。`?surf=0|1|2` 可强制覆盖，
给同机位 A/B 用（跟 `?stats=1`、`?aodebug=` 同一类调试钩子）。

### 途中修掉的两个真 bug

1. **淡出系数用错了频率，近景下法线扰动几乎归零**。整个凹凸乘的是"细八度"的
   淡出系数，而细八度本来就该在那个尺度被淡掉。算出来：骨骼在 0.23 毫米/像素的
   近景下，细八度淡出只剩 **0.03**，基础八度（1.6 毫米的骨面起伏）却还有 0.78——
   于是骨头在近景下一点起伏都没有。`medium` 档更纯粹：它压根不算细八度，
   那个系数在那里只剩副作用。改成两个淡出系数各管各的。
2. **`addFresnelRim` 直接覆盖 `onBeforeCompile`**，谁加在它之后都会被整个吞掉，
   而且吞得无声无息。改成链式（`customProgramCacheKey` 同理），并加单测锁住
   "边缘光与表面质感同时在"。

### 单测 21 条，最值钱的是锚点那几条

验证注入锚点（`#include <project_vertex>`、`<normal_fragment_begin>` 等）
**在 three 的真实着色器源码里确实存在**。皮肤那次就是栽在"锚点变了、replace
静默失效"上——结构没变、数值全对、就是画面不对，单测和 e2e 都拦不住。
three 升级后这里会先红，而不是等人在手机上看出一片光滑。

### 定幅度：我先写错了标准，又靠标定推翻了它

第一版参数保守得几乎不存在。**同机位 A/B 一量就露馅**：局部对比度（相邻像素
亮度差，`scripts/surface-contrast.py`）前景肋骨 1.06×、椎体 0.93×。
我看图时以为"椎体有起伏了"，数字说没有——**眼睛会骗人，这类改动必须量**。

然后我在代码注释里写死了一条"要到 1.5× 才算过"。**这条是错的**，标定推翻了它：

| bump | 局部对比度 | 画面 |
| --- | --- | --- |
| 0.32（第一版） | 1.06× | 看不出 |
| 2.0 | 1.27× | 仍然很弱 |
| **5.0（定稿，骨骼）** | **1.57×** | 骨面起伏、斑驳，像骨头 |
| 20（极端实验） | 1.65× | 揉皱的锡纸 |

**5.0 和毁掉画面的 20 只差 0.08**。局部对比度在这类场景被几何边缘与半透明叠加
主导，比值被压得很扁。所以这个数**只回答"有没有生效"**（1.06× 就是没生效），
**定不了幅度**——注释和脚本输出都已改正。把一条自己写的、听起来很硬的量化标准
留在代码里，比没有标准更糟。

那次 `bump=20` 的极端实验本身是有用的：它一次性排除了"法线扰动根本没进到光照里"
这条岔路（画面剧烈变化 = 机制通畅），省掉了往错误方向查的时间。

### 五个系统逐个看过，按规则推出来的值有两个是错的

**这条是这一轮最实用的教训**：一次性把五档参数按公式推出来然后一起发，
会发出两个坏的。逐个拍图看下来：

| 系统 | 定稿 bump | 初值 | 看图之后 |
| --- | --- | --- | --- |
| skeleton | 5.0 | 5.0 | ✅ 从白塑料变成有骨面起伏与斑驳 |
| vessels | 2.5 | 2.5 | ✅ 干净的管子，高光正常 |
| nerves | 1.5 | 1.5 | ✅ 脑与小脑表面柔和，无夸张高光 |
| muscles | **1.2** | 5.0 | ❌→✅ 初值糊成揉皱的玻璃纸 |
| organs | **1.2** | 3.5 | ❌→✅ 初值是油腻团块与夸张高光，像融化的塑料 |

肌肉的增益明显小于骨骼，原因要说清楚：**BP3D 的网格本来就刻着肌纤维沟**
（A/B 里 `surf=0` 那半边的纹理就是几何来的），这层只是补上色调变化与轻微起伏，
不像骨骼那样是从零到一。

### `bump` 要跟着 `stretch` 反着走

拿肌肉撞出来的：同样的 5.0，骨骼（stretch=1）正好，肌肉（stretch=9）糊成一片
油光。拉伸把噪声在"横过纹理"方向压扁，等于把那个方向的有效频率放大 stretch 倍，
梯度跟着陡峭。

**但这条规则本身也漏了一件事：材质的光泽度。** 按 1/√stretch 算器官该给 4.0
（stretch 只有 1.6），实拍是融化的塑料——器官挂着 clearcoat 0.28 + sheen，
镜面反射会把法线扰动再放大几倍，骨骼那种半哑光材质不会。有意思的是血管更亮
（clearcoat 0.6）却没事：管子太细，噪声铺不开。
**所以规则只用来起头，每一档还是得看图定。**

### 顺带修掉的另一个用户可见 bug：分享链接会丢相机角度

发现方式很偶然：给着色器做同机位 A/B，想用 `?v=` 里的 `cam` 直接摆相机省掉交互，
结果拍出来两张都是默认全身取景。

根因：`toUrlState` 无条件把相机位姿写进 `?v=`，恢复时走 `setCameraPose`——
但它没清 `autoFramed`。紧接着 UI 量完面板高度调 `setSafeInsets`，那里看见
`autoFramed` 还是 true，就"好心"重新框一次全身，把刚恢复的机位顶掉。
带 `selected` 的链接因为随后还会 aimAt 到那个结构，症状被盖掉一半，所以一直没发现；
**纯粹分享一个角度**（转过身、推近了、没选中任何结构）的链接则是整个失效。
已修，并补了一条 e2e——故意不选中任何结构，那才是完全失效的情形。

### A/B 的方法论（踩了三个坑才站稳）

1. **不能用交互摆相机**：双击定心顺带就是拾取，两次跑选中了不同结构，
   对比图里差的其实是高亮状态。改成 `?v=` 的 `cam` 一步到位。
2. **分层值必须取该系统完全不透明的那一档**：骨骼原来放在 0.62，
   而 `layers.ts` 的曲线上那里不透明度只有 0.3——等于隔着 70% 的透明判断质感。
   改成骨骼 0.45、肌肉 0.2。
3. **只留一个系统**（`?v=` 的 `systems` 开关）：整具人体 478 万面在软件渲染下
   一帧一分多钟，调一次参数等十几分钟；只留骨骼是 76 万面，才转得动。

**通则：A/B 里除了要测的那一个变量，别的都得钉死。**

### 中途踩的一个"静默失效"（着色器注入特有）

皮肤改完第一版是**开屏全黑**，而**着色器编译没报错、控制台一声不吭**。
我差点又靠眼睛下结论（"是不是加色混合在暗背景上太淡"），量了像素才确定：
三维区最亮只有 20（就是舞台底色），皮肤一个像素都没画。

根因：世界法线挂在 `<beginnormal_vertex>` 之后，而 `MeshBasicMaterial` 的顶点
着色器里那一句被 `#if defined(USE_ENVMAP) || defined(USE_SKINNING)` 包着——
两个都没有，整段被预处理器编译掉，`vXrayN` 永远不被赋值。
`normalize(未初始化)` 得到 NaN，片元 alpha 跟着成 NaN。**语法完全合法，所以不报错。**

**而先写的那 5 条单测全绿也没拦住**：它们只验证"字符串注进去了"，不验证
"注入点在实际的宏定义下是不是活的"。补了一条专门锁它——断言 `vXrayN` 的赋值
位置在 `USE_ENVMAP` 守卫**之前**。截图脚本也补上了控制台错误捕获。

### 说清楚的一个近似

顺纹方向一律取世界 Z（身体长轴，相机 up 也是 (0,0,1)）。对股四头肌、竖脊肌是对的，
对腹外斜肌、肋间肌这类**斜行肌就差 45°**。这是表面纹理的近似，**不是解剖学的
肌纤维走向**，文案里不能说成后者。要做对得给每个结构存方向向量，而合批下每实例
的通道已被"颜色 + 不透明度"占满，是另一轮改造（DECISIONS 待定）。

### 皮肤退回 X-ray 壳（人类拍板）

**"皮肤功能无法升级细化，就直接去掉，回到原来的皮肤设计。"**

起因是 v1.2 那轮已经量清楚：BP3D 的皮肤到顶了——203,382 面就是原生全部，
而且**没有 UV、贴不了图**，再细化只能换数据源（CC0 体表，人类已暂停）。
与其留一层"努力想像人却不像人"的塑料壳，不如退回一个不假装写实的抽象表达。
皮肤配色一并退回品牌青 `0x4fc3d9`。

**不能直接用回旧实现，这是这次改造真正的坑**：旧版 `createXRayMaterial` 是裸
`ShaderMaterial`，顶点着色器写死 `modelMatrix * vec4(position, 1.0)`，不认合批矩阵；
而皮肤自 v1.1 起走 `BatchedMesh`，glb 顶点又是量化过的（局部坐标在 ±1 附近、
真实尺寸全在节点 TRS 里）——直接用回去皮肤会缩成原点附近的一小团。

改挂在 `MeshBasicMaterial` 上重建：自带 `batching_vertex`，每实例颜色与不透明度
照旧走 `setColorAt` → `vColor`，而且**没有光照计算**——这一层铺满整屏，
省的是实打实的片元开销。补了 5 条单测锁住合批那两处矩阵、逐实例 alpha、
以及加色不写深度。

顺带解释人类截图里胸口/髋部/大腿上的暗斑：那是内层结构从皮肤壳里穿出来
（分层刚离开 0 时内层有一点"底噪"，见 `layers.ts` 的 CURVES 注释）。
换成 X-ray 壳之后这不再是瑕疵——透出内部结构本来就是那个设计的用意。

**4「许多断裂的地方是不是没有修整好」——查清了，不是网格破了，是两处渲染接缝。**

先把"破没破"量掉：48 个骨骼结构**边界边合计 0**——没有一个洞。所以问题不在修整。
把器官/血管/神经全关掉、只留纯骨骼推近看，逮到两处，成因完全不同：

- **肋骨"断"在中段** = 肋软骨的配色。肋软骨是独立结构，配色表给的是 `#c8cfd6`
  冷蓝灰，比骨色 `#d8d3c3` **更暗**（明度 206 vs 211），而它与肋骨是端对端平口相接——
  一段暗色接在亮骨上，就读成"这儿断了"。量过接缝：软骨↔肋骨、软骨↔胸骨的最近距离
  **0.05–0.55 mm（中位 0.12）**，而网格自身平均边长 3.96 mm——它们是贴着的，没有缝。
  改成 `#dfe6ec`（比骨头**更亮**的珠光蓝白，真软骨本来也比干骨亮），现在读成
  "肋骨换了一种更透亮的材质继续往前"，而不是断口。
- **脊柱每一节都"崩了口"** = 椎间盘与椎体互相穿插。实测：靠近椎骨 2 mm 内的椎间盘
  顶点里 **44% 落在椎骨内部**，中位穿插 0.11 mm、最深 **1.76 mm**。两张面在同一处
  来回穿，深度测试没有稳定赢家，交界闪成一圈锯齿。两手一起压：
  ① `pipeline/process.py` 加 `SEAM_INSET_MM`，椎间盘沿法线内缩 **0.5 mm**；
  ② 配色从 `#c9c3ae` 调到 `#d2ccb9`，与骨色的明度差 16 → 7。
  **压下去了但没消干净**，四倍放大仍看得出一条不平的接缝——要彻底干净得内缩到
  1.5 mm，那会削掉两成盘高（椎间盘约占脊柱长度四分之一，这是我们自己奥秘里写的
  数字），不值。正常视距下已经看不见。
